# Native account deletion contract

`DELETE /api/native-account-data` uses a recently authenticated Firebase bearer token. It accepts no body, UID, document path, or scope parameters. Google verifies the token and its current account state; authentication and per-person rate limits run before deletion. No Telegram link is required. Native deletion affects only the verified app UID. Reserved `tg_` identities are rejected. Telegram-owned sync roots, chats, wallets, payments, browser sessions and publications are preserved; the app link is removed from both configured stores.

The response is `{ "version": 3, "telegramUnlinked": true, "uid": "<verified subject>", "firestoreDeleted": true, "publicationsDeleted": true, "writesBlocked": true, "removed": 0 }` only after unlinking in both stores, publication cleanup and all discoverable Firestore writes have been acknowledged. The client must validate the version, subject and acknowledgment before deleting Firebase Auth. The server also repeats publication cleanup behind its write barrier, closing the gap after the client's earlier unpublish request. This endpoint neither deletes Auth nor changes the publication API's meaning.

Errors return no private document paths or credentials. Unavailable configuration, failed enumeration, excessive recursion, or a failed/missing per-write status returns 503. Children at every deeper level must succeed before any parent deletion starts. Repeating the operation after a lost response or partial success is supported. The client keeps its login on timeout, missing endpoint, malformed acknowledgment or server failure; it must not fall back to listing documents itself.

## Historical ownership gate

`NATIVE_ACCOUNT_DELETION_READY` controls only native Firebase account deletion. `TELEGRAM_ACCOUNT_DELETION_READY` separately controls Telegram and browser Delete my data. Both are deliberately absent from deployment configuration. Each requires the literal string `true` and Firestore configuration. The legacy shared `ACCOUNT_DATA_DELETION_READY` flag is ignored. Enabling either channel cannot enable the other. Every closed channel rejects before removing account data, browser sessions or links. These are release gates, not substitutes for reconciliation. The user approved native-only deletion with Telegram preservation on 5 November 2026. Production activation still requires the ownership, topology, rules and retention checks below.

Recursive traversal can discover missing parents under `users/{uid}` and `staging_users/{uid}` because the path retains ownership. A deleted top-level study parent loses the owner field used by the query. Revision payloads alone are not universally trustworthy owner evidence: historical rules authorize through a parent and do not enforce every revision owner field.

A safe reconciliation preserves ownership evidence before it deletes anything:

1. Inventory missing top-level study parents and their descendants read-only. Match only to trusted retained parent records, backups, or a server-controlled ownership ledger. Record source evidence and conflicts per study; missing or contradictory ownership remains unresolved.
2. Keep any resolved owner ledger server-controlled and immutable to clients. Remove its UID only after every descendant is acknowledged; keep an owner-free ID reservation so stale requests and clients cannot reclaim the ID. Do not recreate private study content or infer ownership from a caller-supplied study ID, display name, or unenforced revision field.
3. Ordinary study deletion and queued replay now use `DELETE /api/native-studies/:scope/:id`. The server verifies the parent owner and atomically claims a server-only `study_deletion_owners/{root}:{id}` fence with a parent update-time precondition before deleting descendants. Every study deletion chunk compares and advances the fence generation in the same atomic commit as version-conditional deletes. A concurrent parent edit aborts acquisition; a newer erasure invalidates the older fence. The parent remains until descendant deletion succeeds. A second traversal removes late revisions; failures remain retryable through the ledger. Account erasure removes the UID from the ledger last, retaining only version, study root, study ID and `state: "erased"`. The ID is never released for reuse. Already-existing clients that bypass this route and simultaneous account-wide writes still require a reviewed rollout/rules contract.
4. Reconcile historical records through a reviewed dry run, verify isolation and interruption/retry against the actual service contract, and verify deployed configuration/rules. The readiness gate stays closed while any of these conditions is unproven. Enabling it or deleting real records is a separate production action.

`inventoryOrphanedStudyParents` provides the read-only first step for an authorized administrative execution. It paginates both top-level study collections with missing-parent placeholders and a `user.id` projection, returns only orphan parent names, performs no writes, and explicitly reports `ownershipResolved: false`. It is not exposed through HTTP. Its emulator result does not establish production inventory or ownership; trusted evidence must still be supplied and reviewed.

`bot/scripts/inventory-study-orphans.mjs` runs that inventory using an existing `FIREBASE_SERVICE_ACCOUNT` environment binding or `--credential-file`, and requires `--output` to create a new private report (0600). It refuses every Firestore request except projected GET listings of the two study collections, never prints credentials or orphan paths, and does not overwrite reports. `--emulator` accepts only loopback and records the demo project in its output.

The ordinary-study route defaults closed unless `NATIVE_STUDY_DELETION_READY=true`. Before enabling it, verify historical ownership and deployed rules that deny client reads/writes to `study_deletion_owners`, deny client parent-only deletes and block writes and revision reads for ledger/quarantined IDs; both clients and queued replay must use the reviewed route. A stale or unavailable endpoint leaves the deletion queued rather than falling back to a parent-only delete. The new ledger records only ownership proven from a live parent; it is never used to guess ownership of older unrecorded orphans.

The endpoint's unit and local Worker tests are not evidence that historical production orphans have been reconciled. A release with the gate closed cannot claim a functioning complete account-deletion flow. A release with the gate opened without reconciliation cannot claim complete erasure either.

### Continuous verification

The `end-to-end` workflow runs `bot/tests/firestore-admin-emulator.test.mjs` against a real, isolated Firestore emulator in two jobs: this repository's Telegram production rules, and the native production/staging rules pinned to app candidate `198c31124fd6e4c424979839aa0b72f49dfbe90f`. Its `playwright` summary requires both deletion jobs and every browser job to succeed. The native rules are test input only; no workflow in this change deploys rules or enables deletion.

The Telegram rules do not expose staging collections, so their job sets `FIRESTORE_RULES_TEST_SCOPE=production`. The native job exercises both scopes. Both set `REQUIRE_FIRESTORE_EMULATOR=1`, which fails if the emulator host is missing instead of reporting skipped acceptance tests as success. Ordinary `npm test` still runs the synthetic Worker/D1 tests, but its skipped emulator tests are not acceptance evidence.

The emulator checks cover missing-parent history, ownership fences, interruption/retry, quarantine, concurrent edits, and interleaved erasures. The separate rules suite verifies that old clients cannot delete a study parent, write through an account barrier, forge a reservation, or reuse a reserved study ID. These checks do not establish deployed rules, historical ownership, privileged-writer exclusion, or device behavior. When the native candidate changes, update the pinned test input and rerun both contracts before using the results for that candidate.

## Historical ID reuse and unresolved ownership

A missing top-level parent with surviving revisions can be recreated under another account under the earlier create rules. Revision access in the mobile rule file then follows the replacement parent. A live parent today is therefore not sufficient evidence of ownership of all historical revisions. The inventory lists missing parents; it cannot detect IDs already reclaimed before inventory. No production exploitation or absence of orphans has been established.

The proposed rules deny recreation when a server-controlled ledger entry exists and deny revision reads for that ID, including when a replacement parent already exists. An approved reconciliation may quarantine a known uncertain ID with `version: 1`, `state: "ownership-unresolved"`, `studyRoot`, and `studyId`, without a `user.id`. This blocks access without falsely assigning the history to a claimant. Neither inventory nor tests create production quarantine records. Unknown or contradictory owners must stay unresolved until a trusted retained parent, backup, or audit evidence proves ownership; arbitrary revision fields do not do so. Do not erase or assign those records based on the current parent alone.

Both rule candidates still differ in other policies: the Telegram repository permits broader study reads. Select and review the actual deployed rules before any release; running the candidates in an emulator does not establish production policy. Historical reconciliation, prevention of old-client bypass and account-wide concurrent writes remain prerequisites for both readiness flags. Account-wide write exclusion and all-channel publication retention still require acceptance review; these patches do not certify them.

## Read-only inventory with an existing Google identity

In an environment already signed in to Google with authorized Firestore read access, from this repository with its dependencies installed:

```sh
node bot/scripts/inventory-study-orphans.mjs --gcloud --output /private/path/orphan-inventory.json
```

The runner captures `gcloud auth print-access-token --quiet` in memory, never prints it, and never calls login, creates credentials, changes IAM or writes Firestore. An existing `FIREBASE_SERVICE_ACCOUNT` environment binding or `--credential-file /existing/private/key.json` is also supported; never put a key or token in chat. Output is a new mode-0600 file; choose an existing private directory. If no authorized session exists, stop and have an authorized operator run this command in their existing environment. The runner does not acquire access on its own.

The only Firestore requests allowed are paginated GET `projects/cyberjudah-app/databases/(default)/documents/studies` and `.../staging_studies`, using `showMissing=true` and `mask.fieldPaths=user.id`. OAuth token exchange is allowed only for the existing service-account mode. Google documents the [existing-session token command](https://docs.cloud.google.com/sdk/gcloud/reference/auth/print-access-token) and [projected document listing with missing parents](https://docs.cloud.google.com/firestore/docs/reference/rest/v1/projects.databases.documents/list). An inventory result is confidential evidence, not authorization to delete or reassign records.

## Device-write and publication barriers

Before enumerating Firestore, both native and Telegram/browser flows persist server-only `account_deletion_blocks` records for the verified canonical and linked legacy UIDs. The D1 seed barrier is committed before reading the link, and link inserts/updates test those barriers in the same SQL mutation. The Firestore markers are committed and acknowledged together. Proposed personal-data rules reject client writes while a marker exists, including another device and offline queue replay. Markers are outside the erased roots and survive failures and successful cleanup. Custom-token issuance and new ordinary-study deletion requests reject blocked identities.

Publication inserts/updates conditionally execute only when the UID has no D1 deletion barrier. This condition is part of the INSERT statement, not a separate earlier read. Server cleanup coordinates the production and staging publication databases through a named internal `PublicationErasure` RPC entrypoint. Both stores acknowledge barriers for the exact identity set before either cleanup. Each Worker derives its own publication owner using its own privacy key, then deletes only those owners' publications. Missing or mismatched bindings fail closed. A publication failure rejects the attempt and preserves account links; retries retain the barriers. Public study responses now use `Cache-Control: no-store`; older responses already cached by earlier deployments may persist for their previous 60-second freshness interval, and previously downloaded public copies cannot be recalled.

The native client requires version 3, `telegramUnlinked: true`, the matching app UID and all completion acknowledgments; it rejects older responses. Telegram/browser use the same barrier orchestration and do not report success on failed publication cleanup. Minimal deletion markers contain an identifier and, in Firestore, format version only, never study text. They currently have no automatic expiry or unlock. Retention and re-enrollment behavior, especially reuse of a Telegram identity, require review before rollout.

Local integration tests now run two real Workers with separate D1 databases and different privacy keys. They exercise delayed publication, peer failure and retry, missing/misbound peers, mismatched identity acknowledgments and preservation of another account. This does not verify deployed topology, historical ownership or external Admin SDK writers. Under the approved native unlink policy below, Telegram-owned KV/payment records are preserved; the unrelated work on those writers remains isolated from the main release branch and belongs to Telegram's independent acceptance. Neither production rule file is deployed by this change; the broader Telegram rule candidate must not substitute for the owner-only native rules.

## Two-store rollout contract (review only)

`bot/src/worker.ts` preserves the existing default HTTP Worker and exports the named `PublicationErasure` class. The class has no HTTP route. A service binding is a privileged capability to block identities and erase publications, so only the reviewed counterpart Worker may receive it. This patch adds no deployment bindings or readiness variables.

After approving the exact topology, both Workers need their own `PUBLICATION_STORE_ID` (`production` or `staging`). The production binding would be `{ "binding": "PUBLICATION_ERASURE_PEER", "service": "cyberjudah-telegram-staging", "entrypoint": "PublicationErasure" }`; staging needs the symmetric binding to `cyberjudah-telegram`. Verify the deployed D1 IDs are distinct and correspond to those stores, and verify both link graphs under the chosen policy. Do not infer correct physical storage merely from a claimed store label. No secrets are copied between Workers.

Deploy both reviewed entrypoints with all gates closed before adding/activating peer bindings. Verify both `describe` contracts and disposable-account acceptance across both databases. Only then consider separately enabling the reviewed native and ordinary-study gates. Leave Telegram's gate closed until its independent acceptance is complete. Existing Stars purchases, balances, support and payment records are unaffected by this candidate. The linked-account policy is approved as described below; marker retention/re-enrollment, historical ownership, writer inventory and deployed-rule acceptance remain unresolved prerequisites for native activation.

Account-wide cleanup now consults the per-ID ownership ledger even for studies found through a live-parent owner query. Unresolved quarantine or conflicting ownership aborts the entire scan before any Firestore content delete, including unrelated own notes. Earlier publication cleanup and deletion barriers may already have completed; an incomplete result never means that all prior steps were rolled back. This closes the recreated-parent quarantine bypass; both unresolved and conflicting-owner regressions fail before the correction and pass after it.

## Interleaved privileged deletion protection

Firestore list/read versions are retained in deletion plans. No content deletion is unconditional: every write requires the exact `updateTime` observed. Study operations additionally acquire a durable per-ID fence before enumeration, using an atomic ledger claim and parent precondition. Each destructive chunk atomically compares and advances that fence with a fresh random generation, so a newer request invalidates a paused older request. Failed preconditions reject rather than retry stale names. The ledger remains attributable on partial failure; completed account cleanup replaces it with an owner-free tombstone that permanently reserves the ID.

Actual emulator regressions pause both an account erasure and an ordinary-study erasure, let a second erasure finish, attempt client ID reuse, then simulate privileged replacement with another owner before resuming. Client recreation is denied; both stale requests fail and replacement content survives. A separate conditional-write test preserves a concurrent revision edit and its parent until a fresh retry. These are tests of the current candidate, not approval to modify production data. Arbitrary external Admin SDK writers remain outside the client-rule barrier and must be included in operational acceptance.

D1 cloud-backup inserts/updates, top-up reminder inserts/updates and browser-session creation now test the legacy-UID deletion barrier within their SQL mutation. These writes cannot commit after that barrier. Read and deletion operations remain available. This does not serialize credit/payment callbacks or KV-backed chat, daily-verse, reminder and shared class-request writers; those remain blocked release work.

## Native unlink boundary (approved policy, 5 November 2026)

The app UID owns shared Firestore study data even while Telegram can access it through a link. Deleting that app account removes those app-owned studies, including shared views; it does not copy private app data into a Telegram shard. Telegram's `tg_<id>` roots and keyed Telegram-owned D1/KV data remain independent. No historical provenance is inferred from client-created fields. Production ownership/schema verification remains required before enabling this policy.

Before confirmation, the native modal distinguishes app-owned shared study data and displays this consequence in bold: “Deleting your app account will disconnect your Telegram data, but your Telegram history will remain saved on Telegram.” French has equivalent wording. Existing typed confirmation, provider reauthentication and cancellation are retained.

The named RPC advertises `nativeUnlink: 1`. The caller rejects an older/incompatible peer before any writes. It then creates a durable app UID barrier, freezes its Firestore writes, acknowledges D1 barriers in both stores, and unlinks by app UID in each store before content cleanup. Link mutations check the same local SQL barrier; retries cannot attach the deleting UID or unlink a newer UID. Partial unlink, lost acknowledgment and wrong-subject receipts remain incomplete. The native client accepts only the version 3 response with `telegramUnlinked: true` and all other completion fields.

No cleanup record retains the Telegram owner or encrypted link payload. The minimal app UID barriers intentionally survive; they are not anonymous and require a reviewed retention/re-enrollment policy. Native bearer access to Telegram APIs is denied once its barrier exists. A new Telegram sign-in after unlink uses its own reserved UID; stale app UID tokens cannot bypass the candidate Firestore rules. Auth lookup cleanup uses a compare-and-delete so an older in-flight lookup cannot remove a newer link.

This uses durable, idempotent checkpoints in the existing Worker/D1/Firestore architecture. It does not add RabbitMQ/SQS or promise automatic background completion: a failed or timed-out request requires retry while Firebase Auth remains intact. Both channel gates stay closed. These source changes are not a deployment or a claim of legal compliance. Telegram's separate Delete my data flow remains independently gated and deferred.
